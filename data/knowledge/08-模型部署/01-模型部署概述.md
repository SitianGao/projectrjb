# 模型部署概述

## 1. 概念定义

模型部署是将训练好的机器学习模型集成到生产环境中，使其能够对外提供推理服务的完整流程。部署涉及模型格式转换、推理优化、服务封装和运维监控等多个环节。

**部署 ≠ 写一个 Flask API 就跑**。生产级部署还需要考虑：负载均衡、模型版本管理、A/B 测试、监控告警、自动扩缩容、安全防护。

---

## 2. 模型导出

### 2.1 ONNX（Open Neural Network Exchange）

ONNX 是一种开放的模型交换格式，允许在不同框架之间互操作。

- **PyTorch 导出**：`torch.onnx.export(model, dummy_input, "model.onnx")`
- **TensorFlow 导出**：`tf2onnx` 或官方转换工具
- **Sklearn 导出**：通过 `skl2onnx` 库将传统 ML 模型转为 ONNX
- **优势**：跨框架互操作、硬件加速支持（TensorRT / OpenVINO / ONNX Runtime）
- **注意**：动态形状和自定义算子可能需要特殊处理（如 `torch.onnx.export(..., dynamic_axes={...})`）

### 2.2 常见序列化格式

| 格式 | 框架 | 特点 |
|------|------|------|
| **PyTorch (.pt/.pth)** | PyTorch | `torch.save(model.state_dict())` 保存权重；TorchScript: `torch.jit.script(model)` 保存完整图 |
| **TensorFlow SavedModel** | TensorFlow | `model.save()` 导出目录，包含计算图+权重+签名 |
| **ONNX** | 通用 | 跨框架中间表示，是部署生态的核心枢纽 |
| **TensorRT (.engine/.plan)** | NVIDIA | 针对特定GPU深度优化的推理引擎，极致性能 |
| **OpenVINO (.xml+.bin)** | Intel | 针对 Intel CPU/GPU/VPU 优化 |
| **CoreML (.mlmodel)** | Apple | iOS/macOS 设备端推理 |
| **TFLite (.tflite)** | Google | 移动端和边缘设备推理 |
| **GGUF / GPTQ** | LLM专用 | 量化后的大语言模型格式，用于 llama.cpp / vLLM |

### 2.3 TorchScript

TorchScript 是 PyTorch 的图模式子集，可以在没有 Python 解释器的 C++ 环境中运行。

- **Tracing**：`traced = torch.jit.trace(model, example_input)` — 跟踪一次前向传播，记录操作序列
- **Scripting**：`scripted = torch.jit.script(model)` — 解析 Python 代码编译为 IR
- **Tracing 的陷阱**：无法捕获控制流（if/for 依赖于输入时），此时需要 scripting
- **混合方案**：对主干用 tracing，对控制流部分用 `@torch.jit.script` 装饰器

## 3. 模型优化

### 3.1 模型量化（Quantization）

将模型参数从高精度（FP32）降到低精度（INT8/FP16/INT4），减小模型体积和推理延迟。

**量化类型对比：**

| 方法 | 精度 | 速度提升 | 实现复杂度 |
|------|------|---------|-----------|
| FP16 推理 | 几乎无损 | 1.5-2× | GPU 原生支持，零成本 |
| INT8 PTQ (训练后量化) | 微小损失(<1%) | 2-4× | 需要校准数据集 |
| INT8 QAT (量化感知训练) | 几乎无损 | 2-4× | 需要重新训练或微调 |
| INT4 (GPTQ/AWQ) | 可接受 | 4-6× | 需要专门量化算法 |

**PTQ (Post-Training Quantization)**：
1. 在已训练模型上运行校准数据集（几百张图/几千条文本即可）
2. 统计每层激活值的分布范围（min/max 或 percentile）
3. 确定每层的量化参数（scale, zero_point）
4. 将权重和激活值量化为 INT8

**QAT (Quantization-Aware Training)**：
1. 在模型中插入 FakeQuantize 节点（前向模拟量化误差，反向用直通估计 STE）
2. 以较小的学习率微调几个 epoch
3. 导出时将 FakeQuantize 替换为真正的 INT8 操作
4. 精度通常优于 PTQ，适合量化敏感模型

**LLM 量化方案：**
- **GPTQ**：基于 Optimal Brain Quantization，逐列量化权重矩阵，每次量化后补偿剩余权重
- **AWQ (Activation-Aware Weight Quantization)**：根据激活值重要性保护关键权重通道
- **GGUF (llama.cpp)**：INT4/INT5/INT8 量化 + CPU 推理，消费级硬件运行大模型的标准方案
- **bitsandbytes**：支持 QLoRA（4-bit 量化 + LoRA 微调）

### 3.2 模型剪枝（Pruning）

移除模型中不重要的权重或神经元，减少计算量。

| 类型 | 方法 | 硬件加速 |
|------|------|---------|
| **非结构化剪枝** | 将接近零的权重置零，生成稀疏矩阵 | 需要稀疏硬件支持（NVIDIA A100+ 的 2:4 稀疏） |
| **结构化剪枝** | 移除整个通道/注意力头/层 | 直接减少矩阵维度，通用硬件加速 |
| **迭代剪枝** | 多次剪枝+微调，逐步压缩模型 | — |

**实践建议**：
- 结构化剪枝 > 非结构化（硬件友好）
- 剪枝率：从 10-20% 开始，逐步增加到 40-50%
- 每次剪枝后必须微调恢复精度
- 大模型（LLM）通常不剪枝，因为稀疏性收益不如量化

### 3.3 知识蒸馏（Knowledge Distillation）

用大型教师模型（Teacher）指导小型学生模型（Student）训练。

$$L_{total} = \alpha \cdot L_{hard}(y_{student}, y_{true}) + (1-\alpha) \cdot T^2 \cdot L_{soft}(p_{student}, p_{teacher})$$

其中 $T$ 是温度参数（Temperature），$T>1$ 使 softmax 输出更平滑，暴露教师模型学到的类间相似性。

**应用场景**：
- BERT → DistilBERT（体积减40%，速度提60%，精度保留97%）
- GPT-4 → GPT-4o-mini
- ViT-Large → MobileViT（移动端视觉Transformer）

### 3.4 其他优化技术

- **算子融合 (Operator Fusion)**：合并 Conv+BN+ReLU 为一个算子，减少内存读写和 kernel launch 开销
- **常量折叠**：编译期预计算确定性的操作（如 BatchNorm 的 running_mean/var 直接融入卷积权重）
- **图优化**：去除推理不需要的节点（Dropout、损失函数、梯度相关操作）
- **推理引擎自动优化**：TensorRT、ONNX Runtime、OpenVINO 在加载模型时自动应用以上优化

## 4. 推理服务部署

### 4.1 Flask / FastAPI 推理服务

将模型封装为 HTTP API，客户端通过 REST 请求获取推理结果。

**基本流程**：
1. 服务启动时加载模型到 GPU 内存（全局单例，所有请求共享）
2. 定义 POST 端点 `/predict`，接收 JSON 输入数据
3. 预处理输入（resize、normalize、tokenize等）→ 模型推理 → 后处理输出
4. 返回 JSON 格式的推理结果

**生产环境增强**：
- **Gunicorn + Uvicorn**：多 worker 进程处理并发请求
- **请求队列**：使用 Redis 做缓冲，防止突发流量压垮 GPU
- **动态 Batching**：将短时间窗口内的多个请求合并为一批同时推理
- **模型预热 (Warmup)**：启动时运行几次空推理，避免首次请求延迟（CUDA kernel 编译、内存分配）

### 4.2 OpenCV 推理 (DNN 模块)

使用 OpenCV 的 dnn 模块加载 ONNX 模型进行推理，适合边缘设备和场景：

```python
import cv2
import numpy as np

# 加载模型
net = cv2.dnn.readNetFromONNX("model.onnx")

# 预处理：blob = (N, C, H, W) 格式，均值减法，缩放
blob = cv2.dnn.blobFromImage(
    img, scalefactor=1/255.0, size=(224, 224),
    mean=(0.485, 0.456, 0.406), swapRB=True
)

# 推理
net.setInput(blob)
output = net.forward()
```

### 4.3 专用推理引擎对比

| 引擎 | 厂商 | 适用硬件 | 特点 |
|------|------|---------|------|
| **TensorRT** | NVIDIA | NVIDIA GPU | 极致性能，需要构建引擎（几分钟），支持 INT8/FP16 |
| **ONNX Runtime** | Microsoft | CPU/GPU 多厂商 | 通用性好，开箱即用，集成简单 |
| **OpenVINO** | Intel | Intel CPU/GPU/VPU | Intel 硬件上的最优方案 |
| **vLLM** | 开源社区 | NVIDIA GPU | LLM 专用，PagedAttention 实现高吞吐 KV-cache |
| **llama.cpp** | 开源社区 | CPU (Apple Silicon/Intel) | 消费级硬件运行量化 LLM 的首选 |
| **TensorFlow Serving** | Google | CPU/GPU | TF 生态的原生方案，gRPC + REST |
| **Triton Inference Server** | NVIDIA | NVIDIA GPU/CPU | 多框架支持，动态 batching，模型编排 |
| **SGLang** | 开源社区 | NVIDIA GPU | LLM 专用，结构化生成 + RadixAttention |

### 4.4 后处理流程

**分类任务**：
1. Softmax → 概率分布
2. argmax / Top-K → 获取类别
3. 可选：置信度校准（Temperature Scaling, Platt Scaling）

**检测任务**：
1. 置信度过滤（如 score > 0.5）
2. NMS（非极大值抑制）去除重叠框
3. 坐标反归一化（从 [0,1] 映射回原始图像尺寸）
4. 标签映射（数字 ID → 人类可读标签）

## 5. LLM 部署专题

大语言模型（LLM）的部署有其特殊性：模型巨大（7B-405B参数）、自回归生成、KV-cache 管理。

### 5.1 KV-Cache 管理

在自回归生成中，每个新 token 需要与所有历史 token 做 attention。KV-Cache 将历史 K 和 V 向量缓存起来，避免重复计算。

**PagedAttention (vLLM 核心创新)**：将 KV-Cache 切分为固定大小的 "pages"（类似操作系统虚拟内存）：
- 按需分配，减少碎片化内存浪费
- 支持 memory sharing（beam search 中共享 prefix cache）
- 吞吐量比 HuggingFace Transformers 提升 **10-20×**

### 5.2 连续 Batching

传统静态 batching：等所有请求完成才能开始下一批。
**连续 Batching (Continuous/In-flight Batching)**：请求一完成就从 batch 中移除，新请求随时加入。

### 5.3 推测解码 (Speculative Decoding)

用小模型（draft model）快速生成候选 token 序列，大模型（target model）并行验证：
- 接受匹配的 token
- 拒绝不匹配的 token，从该位置用大模型重新生成
- 在保持精确输出的前提下，推理速度提升 **2-3×**

### 5.4 常用 LLM 部署框架

| 框架 | 适用场景 | 核心特性 |
|------|---------|---------|
| **vLLM** | 在线推理服务 | PagedAttention, 连续batching, OpenAI-compatible API |
| **llama.cpp** | 本地/边缘部署 | CPU推理, GGUF量化, Apple Silicon优化 |
| **Ollama** | 个人/开发者 | 基于llama.cpp, 一键运行, 模型管理 |
| **Text Generation Inference (TGI)** | 生产级服务 | HuggingFace官方, 支持量化+张量并行 |
| **SGLang** | 结构化生成 | RadixAttention, 约束解码, JSON模式 |
| **TensorRT-LLM** | NVIDIA GPU极致性能 | 图优化+内核融合, 需要构建引擎 |
| **ExLlamaV2** | 本地推理 | GPTQ量化, 高速推理内核 |

## 6. MLOps 与模型生命周期管理

### 6.1 模型注册中心

- **MLflow Model Registry**：版本管理 + stage 管理（Staging → Production → Archived）
- **Weights & Biases Model Registry**：与实验追踪集成
- **HuggingFace Hub**：社区模型共享 + 版本管理 + 推理端点

### 6.2 A/B 测试与金丝雀发布

- **A/B Testing**：新旧模型各服务一部分流量，对比核心指标
- **Canary Deployment**：逐步增加新模型流量比例（1%→5%→25%→100%）
- **Shadow Mode**：新模型接收全部流量但不返回结果，仅记录用于离线评估

### 6.3 监控告警

- **模型性能指标**：延迟（P50/P95/P99）、吞吐量（QPS）、GPU 利用率
- **模型质量指标**：预测分布偏移（data drift）、输入异常检测、输出合理性校验
- **基础设施指标**：CPU/内存/GPU 使用率、请求队列长度、错误率

## 7. 部署最佳实践

- **模型预热 (Warmup)**：启动时运行几次空推理，避免首次请求延迟高峰
- **健康检查**：提供 `/health` 和 `/ready` 端点，配合 Kubernetes 的 liveness/readiness probe
- **超时与重试**：设置合理的请求超时（30-60s），客户端实现指数退避重试
- **资源隔离**：推理服务和 Web 服务分离部署，防止相互影响
- **Docker + K8s**：容器化部署，使用 K8s 管理 GPU 资源分配和自动扩缩容
- **版本管理**：每次模型更新打 tag，保留最近 3 个版本用于快速回滚
- **安全**：输入输出安全过滤、速率限制、认证鉴权、TLS 加密传输

## 8. 常见误区

- ❌ **量化后精度一定会大幅下降** → ✅ INT8 PTQ 通常精度损失 < 1%，INT4 量化（AWQ/GPTQ）在大模型上损失也很小
- ❌ **部署就是写一个 Flask API** → ✅ 生产级部署还需考虑负载均衡、模型版本管理、A/B 测试、监控告警、自动扩缩容
- ❌ **ONNX 模型总是比原框架快** → ✅ ONNX 主要价值在于跨框架互操作，推理速度取决于运行时引擎（TensorRT > ONNX Runtime > 原生框架）
- ❌ **模型越小推理越快** → ✅ 量化后的小模型确实更快，但剪枝产生稀疏性不一定能转化为实际加速（取决于硬件稀疏支持）
- ❌ **GPU 一定比 CPU 快** → ✅ 对于小模型、小 batch，CPU 推理可能比 GPU 更快（GPU kernel launch 和 PCIe 传输有固定开销）

---

## 9. 关键要点

- 模型导出（ONNX/TorchScript/TensorRT）是部署的第一步，选择合适格式取决于目标硬件
- 量化（INT8/FP16/INT4）在保证精度的前提下可显著降低推理成本（2-4×加速，75%体积缩减）
- **TensorRT** 提供极致的 NVIDIA GPU 推理性能，适合对延迟敏感的生产场景
- **vLLM + PagedAttention** 是 LLM 在线服务的当前最佳实践
- Flask/FastAPI 适合轻量级推理，生产环境建议搭配 Gunicorn + 动态 batching
- 后处理逻辑与模型推理同等重要，直接影响最终业务效果（NMS、坐标映射、置信度校准）
- MLOps 是生产部署的必要投资——模型版本管理、A/B 测试、监控告警缺一不可
- **Docker + Kubernetes** 是生产环境部署的标准方案，GPU 资源调度和自动扩缩容都依赖 K8s 支持

> **建议核实**：各推理引擎的性能基准以官方最新 benchmark 为准。框架版本快速迭代，建议参考 vLLM/TensorRT-LLM 的 GitHub README 获取最新性能数据。
